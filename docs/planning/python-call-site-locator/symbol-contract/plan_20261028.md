## Grounding facts (read before writing code)

From `src/tenon/detect/record.py` and `src/tenon/detect/diff.py`:

- `Change.location` is `Location(pointer, method, path)`; `method`/`path` are set only for
  operation-level records (`_record_location`), and `None` for component-schema records.
- `property_removed` / `parameter_removed` / `*_type_changed`: `before` is a rendered dict with
  `name`, `type`, `format` (`_render_type`), plus `in` for parameters.
- `property_required_added` / `parameter_required_added`: `before` is `None` when genuinely added;
  a non-`None` `before` means the item existed and only became required.
- `property_added` / `parameter_added` do not exist as kinds; additions arrive as `*_added` or
  `*_required_added`.
- `renamed`: `before` = old name (**string**), `after` = new name, and `location` points at the
  **new** document. Search the old name.
- `endpoint_removed` / `endpoint_added`: `before`/`after` are path strings; `location.method` and
  `.path` are set.
- `enum_narrowed`, `schema_added`, `schema_removed`: no locatable Python symbol.
- **`operationId` is not in a `Change`.** Never attempt to read it.

## Phases

### Phase 1: `Query` + scope + name extraction (TDD)

- **Files:** `src/tenon/locate/query.py`, `tests/locate/test_query.py`
- **Steps:**
  1. Failing table test over **all 13 `ChangeKind` values** built from literal `Change` objects (no
     spec loading). Every case asserts either a populated `Query` or `reason is
     LocateReason.UNSUPPORTED_CHANGE_KIND`; the test fails if any case raises.
  2. Additional tests for malformed payloads: `property_removed` with `before=None`,
     `before={"type": "string"}` (no `name`), and `before` as a string → `UNSUPPORTED_CHANGE_KIND`,
     never `KeyError`/`AttributeError`.
  3. Implement `@dataclass(frozen=True, slots=True) class Query` with the fields from the spec:
     `scope`, `kind`, `method`, `path`, `operation_candidates`, `field_name`, `change_field`,
     `field_presence`, `origin`, `reason`.
  4. Implement `derive(change, config) -> Query`:
     - `scope = "operation"` iff both `location.method` and `location.path` are truthy.
     - `_field_name(change)` returns `(spec_name, python_name, presence)` per kind: read
       `before["name"]` for removed/renamed/type-changed, `after["name"]` for added kinds, and
       `before`/`after` strings for `renamed`.
     - `field_presence`: `must_exist` for removed / renamed / type-changed, `must_be_added` for
       added / required-added, `absent` for endpoint queries.
- **Validation:** `uv run pytest tests/locate/test_query.py`
- **Commit:** `feat(locate): derive a locate query from a change record`

### Phase 2: Explicit mapping (TDD)

- **Files:** `src/tenon/locate/query.py`, `tests/locate/test_query.py`
- **Steps:**
  1. Tests: `operations={"DELETE /v1/charges/{id}": "charges.delete"}` resolves for an
     `endpoint_removed` with that method+path; method match is case-insensitive (`delete` and
     `DELETE` both match). `fields={"Charge.amount": "amount_cents"}` on a component change whose
     pointer is `#/components/schemas/Charge/properties` sets `field_name="amount_cents"` and
     `change_field="amount"`.
  2. Test that a mapping for a different schema does not apply (no cross-schema bleed).
  3. Implement `_schema_name(pointer)`: split the RFC 6901 pointer on `/`, unescape `~1`/`~0`,
     return the segment after `schemas`, else `None`.
  4. Lookup order: explicit operation mapping (key `f"{method.upper()} {path}"`) → explicit field
     mapping (key `f"{schema}.{spec_name}"`) → inference. `origin` records which won.
- **Validation:** `uv run pytest tests/locate/test_query.py`
- **Commit:** `feat(locate): apply explicit operation and field mappings`

### Phase 3: Inference (TDD)

- **Files:** `src/tenon/locate/query.py`, `tests/locate/test_query.py`
- **Steps:**
  1. Tests, exactly the spec's examples:
     - `DELETE /v1/charges/{id}` → `("charges.delete",)`
     - `GET /v1/customers/{id}` → `("customers.get", "customers.list", "customers.retrieve")`
     - `POST /v2/files/{id}/refunds` → `("files.refunds.create",)`
     - `/legacy` → `("legacy.delete",)` or empty if no usable segment; assert whichever the
       implementation chooses and document it in the test name (a one-segment path with no verb
       name is still a candidate).
  2. Implement `_segments(path)`: split on `/`, drop empties, drop a leading `v<digits>` segment,
     drop `{param}` segments, keep the rest in order.
  3. Verb leaves: `get → ("get","list","retrieve")`, `post → ("create",)`,
     `put|patch → ("update",)`, `delete → ("delete",)`. Unknown method → `origin="none"`,
     `reason=OPERATION_NOT_MAPPED` (the enum lands in aspect 1 when needed; until then return
     `reason=None` and let aspect 4 decide — do not widen the enum in this aspect without updating
     the spec).
  4. Candidates are tuples, built in the documented order; never from a `set`.
- **Validation:** `uv run pytest tests/locate/test_query.py`
- **Commit:** `feat(locate): infer operation and field candidates from path and names`

## Testing strategy

- Pure unit tests: no fixture repo, no filesystem, no `ast`.
- The 13-kind table is the regression net; extend it, never replace it when behaviour changes.
- Run the full suite before each commit.

## Edge cases

- A `parameter_type_changed` record carries `before` with `name` and *also* `after`; use `before`
  for `must_exist`.
- A `renamed` endpoint record (`before`/`after` are paths) has no `field_name`; the query is
  operation-only, and the old path is `change_field` for reporting.
- A component pointer not under `#/components/schemas/` (should not happen in T1, but do not crash)
  → `schema=None`, mapping skipped, inference on the bare field name.
- Empty `path` or `method` with an operation-ish kind → treat as component scope and rely on the
  field name; do not raise.
- Inferred `field_name` is the spec name verbatim — do not snake_case or pluralise it.
